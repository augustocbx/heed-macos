# SMB/Samba synchronization

In Settings, add an SMB/Samba destination, give it a name, and optionally enter a credential-free `smb://server/share` address. **Open macOS connection flow** opens the OS connection window; authentication and Keychain credentials belong to macOS. Heed neither mounts shares itself nor installs a Samba server. A running Heed menu app handles the native folder picker. Select a folder on an already mounted share, test access, and connect. A new destination requires explicit confirmation to create an empty `Heed Library` subfolder. Existing arbitrary content is never adopted as a library.

The destination header is `heed-library.json` with exactly three fields: `format: heed-portable-library`, `schemaVersion`, and an immutable `destinationId` UUID. New empty destinations use `schemaVersion: 2`; existing v1 destinations keep their original header and protocol and are never converted in place. This container identity is independent of each meeting's origin library UUID. Imports retain origin identities and immutable revision ancestry across devices. Each Mac keeps its own connection names, selected paths, mount identities, private queue and native authorization bookmark. These fields are never part of portable meeting exports.

Up to eight named destinations can be retained; one is enabled at a time on this Mac. Enabling a destination pauses the previous one. Rename, disable and disconnect do not change recording settings or delete meetings. Disable retains queued publication jobs. Disconnect removes this Mac's connection configuration; local revisions remain in the portable catalog and a later connection can queue eligible revisions again. An unresolved original v2 operation blocks reconnect or disconnect until its original operation is recovered.

[Physical remote metadata deletion](remote-deletion.md) is a separate explicit action for writable v2 destinations. Review the selected revisions and current destination, then confirm the exact preview. The operation removes selected commit markers, meeting payloads and original manifest contents, retaining a small canonical deletion descriptor to prevent publication of the same revision. Local meetings and AI content are preserved. Shared audio garbage collection is disabled in production; content-addressed audio remains retained. SMB deletion remains pending cross-device verification, rather than claiming complete remote erasure.

## Mount, access and security checks

The native adapter uses public Darwin `fstatfs` to require `smbfs`, bind the selected filesystem ID and hash of the server/share mount source, and recheck descriptors during every operation. Credentials are stripped before hashing; raw mount sources, `smbutil` output and OS error strings are never included in API errors or logs. Every path component is opened relative to a retained directory descriptor with `O_NOFOLLOW`. Losing a mount or replacing it at the same path cannot create an ordinary local directory or redirect a write into the replacement. A legitimate remount can have a new filesystem ID: explicitly test and reconnect the existing destination to accept it, with the same destination UUID.

The public, scoped `smbutil statshares -m <selected mount> -f json` diagnostic reports the negotiated dialect and active protection. `SIGNING_ON` establishes active signing. `ENCRYPTION_REQUIRED` on SMB 3 establishes required share encryption. `SIGNING_SUPPORTED` and `ENCRYPTION_SUPPORTED` describe capabilities and are insufficient. SMB 1, unavailable diagnostics and unverified protection block synchronization. An encrypted connection cannot silently fall back to signing. MacOS owns session authentication; Heed tests actual access and does not independently verify a server-side user identity or store authentication secrets.

Existing v1 libraries on read-only mounts or without publication capability remain available for verified text import. V2 requires writable coordination access even for reads; a read-only v2 destination cannot be opened. A read-only public volume-capability check rejects unsupported new/v2 destinations before remote header or transaction-claim creation. On eligible volumes, the write-access probe tests fsync, atomic exclusive publication and read-back in uniquely named temporary files, then removes only those probes. Heed does not weaken OS or server security settings to make a connection succeed.

Both actual macOS NAS mounts rejected exclusive file/directory rename with `ENOTSUP`; exclusive hardlink publication was also unsupported. The negotiated SMB 3.1.1 signing and authentication passed their narrow prerequisites, but do not establish the mounted filesystem's required atomic operations. Unsupported volumes are not upload-capable. Ordinary overwrite rename, adopting an unknown target or taking over another operation's claim is not a fallback. An alternative SMB server has not been demonstrated to bypass this mounted-client limitation; a different publication protocol requires a separately reviewed versioned design. See the [actual compatibility evidence](qa/remaining-acceptance.md#actual-macos-smb-compatibility).

## Publication and recovery

The shared portable format specifies immutable content-addressed media, meeting JSON, manifests and independent per-device commit markers. The marker is published last, after all referenced artifacts are complete and verified. V2 admits the canonical manifest before transferring payload or media, so an existing deletion fence blocks publication of that revision. The adapter streams bounded data, verifies exact lengths and SHA-256, fsyncs temporary objects, and uses public `renameatx_np(RENAME_EXCL)` to publish without overwriting an existing revision or fence. V1 retains its original publication ordering. Identical immutable-object retries are idempotent; conflicting content fails closed. Stable connection-owned temporary names bound interrupted retry debris; only that exact connection's unfinished temporary object is reclaimed. A separate stable connection-owned lock is held through stage publication and cleanup, so a retry cannot reclaim a live writer's stage. Ordinary synchronization preserves other devices' temporary files and committed data; only separately confirmed deletion removes its exact selected metadata.

V2 publication, import, audio download and deletion hold a persistent exclusive-create destination claim. A crashed or ambiguous operation can leave that destination unavailable. Recovery requires the original private journal, physical Mac, app-directory identity and guard inode; copied journals, expiration and automatic claim stealing do not authorize takeover. Durable checkpoints and atomic whole-claim release protect a later owner's operation. Preserve unresolved private and remote recovery state and use the [original-owner recovery controls](remote-deletion.md); do not manually remove claim files.

Confirmation reads back the marker, manifest, finalized transcript and every referenced audio object and verifies their hashes. This is a **share acknowledgment**, not evidence that data survives server power loss. MacOS and SMB caches, server filesystem flushing, storage controllers and server configuration define the physical durability boundary. Test server restart and power-loss durability separately for the actual deployment.

The private atomic queue is bounded to 10,000 revisions per destination. Confirmation is tracked per destination; verification on one share does not acknowledge publication to another share. Audio awaiting another destination's acknowledgment remains protected from local quota eviction. Local revisions are journaled even while the share is offline or remote retries are delayed. Deleting a local source retires its pending jobs independently of destination-scoped discovery and preserves remote revisions. Finalized local audio is protected before the first queue pass; source inspection holds a quota claim before asynchronous hashing and hands protection to durable pending metadata. Restart releases only abandoned inspection claims and retains their original audio. Retries use persisted exponential delays capped at one hour. Recording or other active audio work postpones background synchronization. Network failures do not prevent ordinary local transcription or AI access to already imported complete meetings.

Discovery reads committed text and metadata, never bulk audio. The portable library imports newest eligible text first under the configurable device quota, including staging, replacement copies and catalog/index costs. Text becomes locally searchable and AI-ready only after verified, complete persistence. Audio is downloaded on request. Concurrent divergent revisions remain explicit conflicts; timestamps and clock skew never choose a winner. Disconnecting or evicting cached audio does not delete remote data.

## Device provider selection

The central `ProviderRegistry` stores one preferred connector ID in the device-only `provider-preference.json`, outside portable artifacts and the managed meeting quota. Connector factories register stable IDs without changing selection. Explicit connect or enable actions persist and activate the chosen provider; disconnect clears selection only when that exact provider is current. Startup calls `restore()` after registrations and restores only the available preferred connector. Unavailable accounts retain their preference for reconnect. Asynchronous connection and credential changes use `withMutation` for their entire operation. Only that mutation's owner may change selection; competing library operations remain blocked until it finishes. Synchronization runs afterward in one `withProvider` lease for the entire discovery/import/queue/publication tick and restores the previous UI provider afterward.

Manual synchronization requires the connection ID displayed by the settings tab. If another tab changes the enabled destination, the stale action is rejected before publication. A corrupt private connector or preference file disables optional synchronization without overwriting the file or preventing local recording and complete local text access. While pending synchronization state cannot be read safely, managed meeting media remains protected from quota eviction. Private settings and library HTTP routes reject foreign origins for reads and writes.

`LibrarySnapshot.providerId`, optional `readOnly`, and optional capabilities describe the selected provider. SMB advertises verified signing/encryption and share read-back acknowledgment. Other connectors must report their own supported confirmation boundary; the common interface does not upgrade a local filesystem write into remote verification.

## Validation boundary

Automated tests use synthetic mount identities, temporary local fixtures, isolated HTTP servers and two independent private catalogs. They cover mount loss/replacement, no local fallback, symlink/traversal rejection, immutable collisions, bounded/corrupt transfers, read-only access, protected transport, durable queue controls, quota pressure, metadata-only discovery and explicit creation consent. The native app compiles for macOS 14 and runs address/local-folder self-tests without mounting a share or displaying a permission prompt.

Physical acceptance is still required on the MacBook Air M1 and MacBook Pro M4 Pro: a disposable Samba server and native macOS SMB share; English/Portuguese content; all four UI locales; actual folder permissions and Keychain authentication; mount replacement, sleep/wake, server restart, denied writes, disconnect during a large transfer, Unicode names, quota pressure, concurrent edits and offline AI. macOS 14 compilation does not establish actual macOS 14 SMB interoperability. No real share, account, private meeting or application installation was used in automated validation.

References: [Apple connection workflow](https://support.apple.com/en-za/guide/mac-help/mchlp1140/mac), [Apple filesystem statistics](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fstatfs.2.html), [Apple SMB diagnostic implementation](https://github.com/apple-oss-distributions/SMBClient/blob/main/smbutil/statshares.c), [Samba manual](https://www.samba.org/samba/docs/current/man-html/samba.7.html).

SMB settings and provider preference changes retain a durable transition containing the previous configuration and selection until both commits succeed. An interrupted transition or failed rollback requires recovery: the controller stops automatic synchronization, rejects cached-provider access before native share calls, and protects all finalized local source audio from quota eviction. Startup retains unresolved configuration and reports unavailable synchronization while keeping local meetings and recording status usable. The Settings card explains that configuration and pending copies must be preserved; it disables further SMB actions until recovery. Private SMB configuration, provider preferences and library protection catalogs use the shared bounded regular-file reader without following symlinks.
