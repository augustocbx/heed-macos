# Issue #101 native-menu validation

The menu presents one readiness decision in its status, Start availability, and immediate recovery action. The installed version appears once in the main menu. Automatic recording, settings and permissions, updates, and diagnostics have one-level groups.

## Automated checks

The optimized native build and `--self-test` passed on the final native source revision `9b50be04f1f8b8cce6a569acbde1fc56a692a23f`. The native checks cover grouping, recording actions, unavailable service, disabled Start for missing permissions, active recording and processing priority, permission reports, update states, and all four locale dictionaries. The update-client self-tests, QA permission fixture tests, and client production build passed. The [current-base CI run](https://github.com/augustocbx/heed-macos/actions/runs/37636391060) passed with 921 server tests, 91 client files / 545 client tests, and native menu self-tests.

The isolated QA update transaction upgraded the synthetic app from 0.1.0 to 0.1.1. Verification checked executable replacement, a fresh permission report, and five fixture-data digests. The native Updates menu initiated the transaction through its **Update…** item and confirmation dialog; this was an observed menu action, not merely a CLI fixture run.

After the real QA update, a synthetic denied microphone and screen report produced `attention` with `microphone` and `screenCapture` missing. With the QA Settings submenu open, only the private fixture file was changed to authorized/true. Selecting **Check permissions again** from that native submenu generated a newer report, changed the isolated update record to `authorized` with no missing permissions, and changed the main menu to [Ready to record](evidence/after-permissions-cleared-en.png) with enabled Start; the [Settings submenu](evidence/after-permissions-cleared-submenu-en.png) then read `Capture permissions allowed`. The [intermediate main menu](evidence/after-permissions-en.png) shows the blocker before clearance. This demonstrates menu-driven warning clearance in the QA fixture, not a change to macOS Privacy grants.

## Keyboard, accessibility, localization, and fit

With VoiceOver off, actual keyboard events opened and navigated the current Settings submenu. Down selected **Open settings…**; another Down skipped the disabled **Capture permissions allowed** row and selected **Check permissions again**; Up returned to **Open settings…**; Left selected the parent **Settings and permissions** row; Right reopened the submenu; Escape closed it. Selection and disabled state were read through System Events Accessibility. The menu and submenu Accessibility trees exposed native menu roles, labels, and enabled/disabled state. These AX observations support assistive-technology discoverability but do not by themselves prove spoken output.

VoiceOver was initially off. In a focused follow-up, the isolated QA app's exact PID was verified before opening its menu. With VoiceOver active, its live `content of last phrase` property changed during VoiceOver navigation to `Start recording`, `Stop recording dimmed`, `Automatic recording submenu`, `Settings and permissions submenu 10 items Open settings …`, `Capture permissions allowed dimmed`, `Check permissions again`, `Permission help …`, and `Meeting mode dimmed`. These observed spoken phrases verify labels, submenu structure, and disabled-state announcements for the tested path; they do not cover every menu item. VoiceOver and the QA app were stopped and verified absent. The caption-panel preference and AppleScript-control checkbox were both restored to their original `0` values; restoring the latter required the user's local macOS authentication. VoiceOver Utility was closed afterward.

At 3840×2160 physical / 1920×1080 logical, 120 Hz, the [English](evidence/after-ready-en.png), [Brazilian Portuguese](evidence/after-ready-pt-BR.png), [French](evidence/after-ready-fr.png), and [German](evidence/after-ready-de.png) main menus and every group submenu were captured. The [Automatic recording](evidence/after-automatic-de.png), [Settings](evidence/after-settings-de.png), [Updates](evidence/after-updates-de.png), and [Diagnostics](evidence/after-diagnostics-de.png) German captures include the longest observed labels; visual inspection found no clipping. The same groups were captured in [English](evidence/after-settings-en.png), [Brazilian Portuguese](evidence/after-settings-pt-BR.png), and [French](evidence/after-settings-fr.png); the remaining submenu images are in [evidence](evidence/). The German Settings submenu was 357×272 logical pixels and remained inside the display.

A bounded second-mode check temporarily switched the same Dell U2725QE to 1600×900 logical at 120 Hz. The [main menu](evidence/after-ready-scaled-1600x900-en.png) occupied frame `[754, 31, 216, 272]`, and the [Settings submenu](evidence/after-settings-scaled-1600x900-en.png) occupied `[965, 366, 266, 272]`; both fit entirely on that display. CoreGraphics restored the original mode successfully, and an independent `system_profiler` check confirmed 3840×2160 physical / 1920×1080 logical at 120 Hz. This validates two modes on one display, not every supported Mac display size or scaling mode.

The before/after images, update, and permission checks are synthetic-state UI acceptance. They do not validate physical recording, actual permission dialogs, service recovery, speech output, or all hardware/display combinations. No installed Heed process, production service, recording, real privacy grant, or user meeting data was changed.
